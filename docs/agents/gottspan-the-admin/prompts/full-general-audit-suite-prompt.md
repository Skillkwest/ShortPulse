# Full General Audit Suite Prompt

Use this prompt when you want an agent to run a broad launch-readiness audit sweep for weak spots, breakage risks, stale contracts, ownership gaps, validation gaps, or repo hotspots before the July 7 launch window.

```text
Pursue the goal of performing a full general audit sweep of this repo for launch-risk weak spots and hotspots before July 7. First, write yourself a compact but thorough goal prompt that names the audit scope, the source-of-truth surfaces you will rely on, checkpoint rules, and exact stop conditions; then pursue that goal. This is an audit and triage goal, not an implementation goal: do not make UI, UX, product behavior, architecture, security, pricing, branch, deploy, or data changes unless I explicitly approve a separate implementation lane.

Work from current repo truth, not memory. Fresh-load the repo startup instructions and any scoped instructions required by the surfaces you inspect. Respect the current branch, production-only, production-URL, solo-owner, desktop-first, no-workaround, no-drift, and owner-lane rules. If subagents are available and allowed by the active tool contract, you may use them for bounded parallel audit lanes, but you remain responsible for reconciling their findings against repo evidence.

Sweep the included repo surfaces systematically: root instructions and scripts; frontend routes, protected-route gates, AI Studio, generation, media/reference-grid, project persistence, pricing/credits, admin, auth/session, styles/layout, tests/checks, docs/SOP/ADR/indexes, systems catalog/readiness surfaces, agent folders, artifact homes, and release/branch/worktree posture. Exclude surfaces that repo instructions say are out of default scope unless current evidence shows they directly affect launch readiness.

For each area, identify what could realistically break, why it matters for launch, what file/system/contract owns it, what evidence supports the concern, whether it is code-proven, docs-proven, test-proven, production-proven, or only suspected, and who should own the next action. Do not treat stale docs, old reports, or prior agent claims as truth unless current code or current repo state supports them. Separate actual findings from watchlist concerns.

Checkpoint yourself whenever context is getting heavy, after each major audit lane, or before switching from discovery to synthesis. At every checkpoint, audit your own coverage: what has been swept, what remains, what findings are real, what is only suspected, whether any lane is blocked by dirty worktree or missing evidence, and whether the next step is still inside this audit goal. Continue until the full included repo sweep is complete or a stop condition is met.

Stop conditions: stop when every included audit lane has been classified as clear, finding, watchlist, owner-handoff, or blocked, and you have produced a prioritized launch-risk report with P0/P1/P2 severity, owner, evidence, recommended next proof, and suggested order of attack. Stop immediately if continuing would require implementation, live account mutation, commit/push/deploy/release work, security remediation, production data mutation, mobile-specific work, or crossing into an owner lane without a handoff. Stop if the worktree is too dirty to distinguish current truth from someone else's active changes; report the exact blocked boundary instead of guessing. Stop if further work would mostly create paperwork, duplicate existing truth, or low-ROI churn. Do not continue into fixes by momentum after the audit report is complete.
```
