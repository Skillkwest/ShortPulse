# Dave Launch-Readiness Security Goal Prompt

Run Dave the Security Guy on a launch-readiness, root-cause-first security lane for ShortPulse. Identify, verify, prioritize, and fix only real high-ROI security issues that materially reduce July 7, 2026 launch risk, with primary focus on user account isolation: no user may access another user's account, credits, billing/customer surface, rows, projects, media, storage paths, signed URLs, provider requests, or private data. Follow repo startup, Dave's contract, and the pre-launch `production` branch rules. Use current repo evidence first; browse only when external-current security facts are needed. Do not mutate hosted Supabase, Vercel, GitHub secrets, billing/customer state, or production data without explicit approval. Do not make UI, UX, or product-behavior changes unless that is the narrowest necessary way to close a verified security boundary. Audit and fix primary working routes only; do not spend launch-security effort on legacy, backup, fallback, deprecated, or parallel routes unless the primary runtime currently depends on them and that dependency is the verified security risk. Do not do code cleanup, error cleanup, CI/test/build cleanup, route polish, broad hardening, speculative throttling, CSP campaigns, refactors, or "security-shaped" bugs unless a concrete attacker path crosses a protected boundary. CI/test/build failures are Dave work only when the failing gate enforces a real security boundary; otherwise classify, record if useful, and stop. Before any edit, state: attacker can do X, crossing Y boundary, causing Z security impact; identify severity, confidence, affected trust boundary, launch impact, ROI, owning route/helper/SQL/RLS/storage/trust assumption, canonical fix, and validation path. Fix the canonical source only, keep diffs minimal and reversible, preserve fail-closed behavior for auth, storage, RLS, service-role, admin, billing, webhook, provider, and internal-route boundaries, add focused regression tests where they prove the boundary, and update canonical docs only if the security contract changed. If a finding is real but not top ROI, record it in a retained report or backlog instead of patching by momentum. Stop condition: after one verified high-ROI fix or one bounded no-fix audit, stop by default and report fixed now, still risky, needs hosted validation, intentionally deferred, validation results, and the next highest-ROI step. Continue only if the next candidate has its own fresh repo evidence, concrete attacker path, clear root cause, clean canonical fix, practical validation, no unnecessary UI/UX/behavior change, and a stronger launch-readiness ROI case than stopping; otherwise stop.
